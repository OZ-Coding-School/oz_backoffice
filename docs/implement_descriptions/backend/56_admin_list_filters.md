# 56. 운영진 신청·세션·채팅방 목록 필터

- 상태: 완료 (2026-11-16 병합)
- 관련 PR: #63
- 관련 결정: `docs/decisions.md` A59
- 이전 기록: [55. P15-2 채팅 실시간 수신(SSE)·멘토링 이벤트 안내](55_p15_2_chat_stream_notices.md)

## 배경
Figma에서 운영진 화면을 설계하면서 멘티 상세와 팀 상세에 신청·세션 탭과 채팅 탭을 두기로 했다(F3). 기존 운영진 목록 API는 기수와 멘토로만 거를 수 있어서 이 탭들을 채울 수 없었다. 그래서 프론트엔드에 착수하기 전에 필터를 추가한다(A59). A59의 첫 번째 PR이고, 멘티 목록과 집계는 다음 PR에서 한다.

## 구현 내용

| API | 추가한 쿼리 파라미터 |
| --- | --- |
| `GET /api/v1/admin/cohorts/{cohort_id}/mentoring/requests` | `student_id`, `team_id` |
| `GET /api/v1/admin/cohorts/{cohort_id}/mentoring/sessions` | `student_id`, `team_id` |
| `GET /api/v1/admin/cohorts/{cohort_id}/mentoring/chat/threads` | `student_id`, `team_id` |

- **`student_id`**(수강 등록 `students.id`): 그 수강생의 **1:1 건만** 보여 준다. 그 수강생이 팀원으로서 신청한 팀 신청은 빠진다. 팀 신청·세션은 팀 상세에서 본다.
- **`team_id`**: 그 팀의 건만 보여 준다.
- **세션:** 연결된 신청의 신청자와 팀으로 거른다.
- **채팅방:** 방 주인(1:1 방은 `student_id`, 팀 방은 `team_id`)으로 거른다. DB 제약상 방에는 둘 중 하나만 있다.
- **필터를 함께 주면** 모두 만족하는 건만 나온다. 기존 `status`·`mentor_id`·페이지네이션도 그대로 함께 쓸 수 있다.

**바꾼 계층**

| 계층 | 바꾼 것 |
| --- | --- |
| 리포지토리 Protocol·구현 | `list_by_cohort`에 선택 인자 `student_id`·`team_id`를 추가했다. 기본값은 None이라 기존 호출은 그대로 동작한다. |
| 채팅방 목록 | 직접 쓴 SQL에 조건을 더했다. 빈 페이지일 때 전체 수를 세는 쿼리에도 같은 조건을 넣었다. |
| 서비스·라우터 | 받은 값을 그대로 넘긴다. |
| 테스트용 가짜 리포지토리 | 같은 필터를 적용한다. 신청 가짜 리포지토리는 상태·멘토 필터도 적용하도록 고쳤다. |

## 주요 결정 (사용자 결정, A59)
- 필터는 프론트엔드에 착수하기 **전에** 추가한다.
- `student_id`는 **1:1만** 거른다(팀 건은 `team_id`).
- PR은 2개로 나눈다: ① 목록 필터(이 기록) ② 멘티 목록과 신청·세션 수 집계.

## 구현 세부
- **스키마 변경 없음.** 기존 인덱스를 쓴다.
  - 신청: `(requester_id, created_at)`, `team_id`
  - 채팅방: `(student_id, last_message_at)`, `(team_id, last_message_at)`
  - 세션: 신청과 1:1로 조인한다.
- 채팅방 SQL은 ruff S608을 피하려고 조건을 문자열 리터럴로 직접 적었다.

## 검증
- **통합 테스트**
  - 신청: 1:1만, 팀만, 둘 다(빈 결과), 다른 기수 수강생.
  - 세션: 1:1만(팀 신청의 신청자는 1:1이 없으면 빈 결과), 팀만.
  - 채팅방: 수강생·팀 필터, 빈 페이지의 전체 수도 필터를 따른다.
- **API 테스트:** 신청·세션·채팅방 목록에서 `student_id`·`team_id` 필터가 동작한다.
- **단위 테스트:** 채팅 서비스의 운영진 목록 필터.
